Module 02 · Visual guide

How Terraform logs in to Azure, and what it's allowed to build

Terraform has no permissions of its own. It borrows them from an identity: you, or a service principal. This guide shows how that works, which role to give at which scope, and how to prove which identity ran.

azurerm ~> 4.0 Terraform ≥ 1.9 Exam objectives 2a–2c, 3a–3g
Part A.1

Azure asks two questions on every request

AuthenticationWho are you?

Answered by an identity in Microsoft Entra ID: a user, a service principal or a managed identity. Like the ID badge you show at reception.

AuthorizationWhat may you do, and where?

Answered by a role assignment: a role (what) on a scope (where). Like an access card programmed for certain floors.

Part A.4

Roles and scopes: the smallest key that opens the right door

A role applies at a scope, and everything below that scope inherits it. Lab 2.2 gives the service principal Reader on the subscription and Contributor on one resource group only.

Built-in roles you'll meet in this course

RoleCan doCan grant access?Give it to Terraform when…
ReaderRead everythingNoPlans only, drift detection, data sources
ContributorCreate, change, delete resourcesNoMost deployments (the usual choice)
User Access AdministratorManage role assignments onlyYesThe code creates azurerm_role_assignment
RBAC AdministratorManage role assignments, limited by conditionsYes, limitedThe safer production choice for the row above
OwnerEverything, including accessYesAvoid for automation
Storage Blob Data ContributorRead and write blobs (data plane)NoRemote state with Entra auth (Module 06)
Key Vault Secrets OfficerRead and write secrets (data plane)NoTerraform writes Key Vault secrets (Module 10)

Management plane vs data plane. Contributor can create a storage account or Key Vault, but cannot read the blobs or secrets inside it. Data access needs a data role such as Storage Blob Data Contributor.

Lab 2.2

Create a least-privilege service principal

To create one you need two permissions: Entra ID lets you register applications (default for most users), and you are Owner, User Access Administrator or RBAC Administrator on the subscription. If not, your trainer creates it for you with the same script.

  1. Run the script from the course repository. It creates the service principal with Contributor on your lab resource group, then adds Reader on the subscription.

    .\02-azure-first-deployment\labs\lab02-service-principal\create-spn.ps1 -Student dg
    ./02-azure-first-deployment/labs/lab02-service-principal/create-spn.sh dg

  2. Or run the same commands by hand to see what happens:

    $SUB = az account show --query id -o tsv
# 1. App registration + service principal + secret + Contributor on ONE resource group
az ad sp create-for-rbac --name sp-tf-training-dg `
  --role Contributor `
  --scopes "/subscriptions/$SUB/resourceGroups/rg-dg-lab02" --years 1
# 2. Reader on the whole subscription
az role assignment create --assignee <appId> --role Reader --scope "/subscriptions/$SUB"
    SUB=$(az account show --query id -o tsv)
# 1. App registration + service principal + secret + Contributor on ONE resource group
az ad sp create-for-rbac --name sp-tf-training-dg \
  --role Contributor \
  --scopes "/subscriptions/$SUB/resourceGroups/rg-dg-lab02" --years 1
# 2. Reader on the whole subscription
az role assignment create --assignee <appId> --role Reader --scope "/subscriptions/$SUB"

  3. Map the output to environment variables. The secret is shown once, so copy it now.

    "appId": "0a1b2c3d-…"→ARM_CLIENT_ID
    "password": "Xy8Q~…"→ARM_CLIENT_SECRET
    "tenant": "72f988bf-…"→ARM_TENANT_ID
    az account show --query id→ARM_SUBSCRIPTION_ID

  4. Set them in the terminal where you run Terraform, and only there. Closing the window removes them.

    $env:ARM_CLIENT_ID       = "<appId>"
$env:ARM_CLIENT_SECRET   = "<password>"
$env:ARM_TENANT_ID       = "<tenant>"
$env:ARM_SUBSCRIPTION_ID = "<subscription id>"
    export ARM_CLIENT_ID="<appId>"
export ARM_CLIENT_SECRET="<password>"
export ARM_TENANT_ID="<tenant>"
export ARM_SUBSCRIPTION_ID="<subscription id>"

  5. Clean up when you're done: clear the variables, az login again, terraform destroy, then run delete-spn.ps1 / delete-spn.sh. It removes the role assignments first, then the app.

Prove which identity Terraform used

whoami.tf outputs the azurerm_client_config data source. Run terraform output terraform_identity before and after setting the variables.

With az login (you)

{
  "client_id" = "04b07795-8ddb-461a-bbee-02f9e1bf7b46"
  "object_id" = "<your user's object ID>"
}
# 04b07795-… is the Azure CLI's own app ID:
# you are logged in as a USER

With ARM_CLIENT_* set (the robot)

{
  "client_id" = "0a1b2c3d-…"
  "object_id" = "<the service principal's object ID>"
}
# the service principal's appId:
# Terraform now has ONLY its roles

Troubleshooting

Read a permission error in three parts

Every Azure authorization error tells you who was refused, what they tried, and where. This is the real error from Lab 2.2 step 5:

Error: creating Resource Group "rg-dg-outside": AuthorizationFailed: The client '0a1b2c3d-…' with object id '…' does not have authorization to perform action 'Microsoft.Resources/subscriptions/resourcegroups/write' over scope '/subscriptions/…/resourceGroups/rg-dg-outside'
Who: the client IDWhat: the action refusedWhere: the scope

The fix is always the same shape: give who a role that contains what, at where or a scope above it. Or decide the identity shouldn't do it at all.
